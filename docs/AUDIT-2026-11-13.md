- **Behavioral tests:** build new failure cases on `HookHarness`, the controlled notification mocks, reader cache tests and native audio regressions. The previous test-quality work is useful infrastructure.
- **Packaging and verification:** reuse the native build scripts, Swift resource preparation, source/hash checks, simulator harnesses, localization audit and release checklist. Re-run native checks after native fixes.

## Findings to fix

### B1 — High priority: a failed saved-location read cancels existing prayer alerts

**Confirmed with production-hook reproduction.** `src/use-location.ts:59` catches a storage read error and continues with a null location. It then sets `ready=true` at line 86 without exposing a load failure. `App.tsx` treats location readiness as sufficient to reconcile notifications. `src/use-prayer-notifications.ts:131` cancels owned recurring prayer alerts when the location is null.

Trigger: a user already has a saved location and scheduled prayer alerts; that location's storage read fails temporarily on startup. Result: the app treats an unread location as an absent location and cancels the pending schedule. The reproduction seeded an existing Fajr alarm; it was removed and the hook reported `needs-location`.

**Fix:** distinguish failed reads from a successful empty result. Expose a bilingual retry state, preserve existing alarms while hydration is unresolved, and still let an explicit user-selected replacement location establish readiness. Reuse the preferences/books read-failure pattern. Test failed read → no cancellation, successful retry → normal reconciliation, and explicit location replacement during failure.

### B2 — High priority for user data: save failures are silently discarded

**Confirmed with production-hook reproduction for both preferences and Quran books.** `src/use-preferences.ts:69` and `src/use-quran-books.ts:34` queue writes but consume rejections without a user-visible save error or retry. The screen continues showing the new value, `ready=true` and `loadFailed=false`. After relaunch, the older saved value returns.

Trigger: storage rejects a write, for example because the device is full. The reproduction changed the interface language and a reading copy's page; both changes disappeared after remounting the hooks. The same books write path stores bookmarks and book names.

**Fix:** add write-failure state independently of read-failure state, retain the latest unsaved snapshot, expose a bilingual retry action, and keep ordered writes. Reuse the Swift port's visible storage-warning concept without requiring a destructive reset for a temporary failure. Cover failed write, retry, relaunch, and a newer edit while retry is pending. The location/theme persistence paths also suppress write errors and should be included in that follow-up.

### B3 — Medium priority: a late Swift GPS result can replace a confirmed alternative

**Source-level race; not executed against Apple frameworks on this Linux host.** `LocationViews.swift:190` commits a city/map/manual selection without cancelling an outstanding device request. `DeviceLocation.swift:86` accepts a later result while `wantsFix` remains true. `AppStore.swift:78` unconditionally assigns that result to `state.location`.

Trigger: start Use my location (or resume with a stale device fix), then confirm a city/manual/map location before GPS completes. The outstanding device request can subsequently replace the user's choice and rebuild prayer alerts for different coordinates.

**Fix:** make location selection an AppStore operation, invalidate/cancel older device requests when an alternative is confirmed, and gate callbacks by request identity. Add controlled delayed-fix tests and verify the actual permission/location flow on Apple hardware or a simulator. Retain the nonblocking authorization callback work from Swift build 5.

### B4 — High priority before the next release: the dependency security inventory has changed

**Confirmed by a fresh `npm audit --json` and installed dependency paths on 13 November.** The audit reports 10 affected package entries: 3 high, 6 moderate and 1 low, with no critical entries. These are package-entry counts, not ten independent vulnerabilities.

Direct advisory-bearing packages are installed transitively through Expo tooling: `node-forge@1.4.0`, `zod@3.25.76`, `glob@13.0.6`, `minimatch@10.2.6`, and `deepmerge@4.3.1`. Other entries propagate those findings through Expo parent packages. Audit reports fixes available. This does not establish exploitation or an affected Quran/prayer runtime path.

`docs/DEPENDENCY-SECURITY.md` describes the 21 October inventory and local patches for two earlier advisories. Today's audit includes additional Forge advisories and other packages; passing the existing eight security tests only establishes their covered mitigations. The exact-version/source-hash patch script intentionally rejects changed dependencies, so replacing packages must include a reviewed patch-script update.

**Fix:** prepare a compatible Expo/tooling dependency update, replace applicable local patches with fixed upstream versions, refresh the security documentation and retain meaningful regression checks. Verify with a fresh install, audit, complete checks, mobile exports, native project generation and relevant builds. Do not blindly apply a major-version audit fix or remove the current patches before the replacements are verified.
